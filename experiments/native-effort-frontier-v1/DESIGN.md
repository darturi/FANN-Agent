Prepared October 24–25, 2026, after the [B1a audit](../../../research/fannagent-b1a-search-effort-audit-2026-10-24.md). This contract is frozen in the sealed package before any new native measurement. ## Question, references and permitted interface

Does native `hnsw.ef_search=320` offer any useful quality/latency frontier against the unchanged **640 study reference**, on the current physical index 90f4a709… / file dbc14b09… and module e7dcace1…? `640` is the P1–P3 study setting, not a verified production or upstream default. Preserve the inspected origin settings (320), record PostgreSQL setting/default/source metadata, and include an unwrapped source-settings comparator. Claims are restricted to these study/source paths. Upstream default performance is not measured.

The experimental v1 envelope is `{version, effort, query}`. Only integer320/640 are accepted, booleans rejected. A strict existing snapshot query validator precedes parsing of the actual predicate and `k`; query IDs and evaluator labels cannot select effort. Known contexts are k10 with no filter, `m_000000 >= 32`, or `>=108`. Other valid contexts conservatively use640; malformed queries reject. No selector is fitted. Forced320/640 arms exercise exactly the same interface. A short320 result is recorded as a quality failure, never silently rerun at640.

Wrapped sessions own two immutable effort-bound reader backends in one private restored database and share a once-loaded immutable snapshot. Connections are admitted and bound eagerly, sequentially. Origin source manifests remain unchanged; a separate effective binding changes only ef_search. Original640 uses the unchanged ordinary-native execution method with a declared640 binding view; source uses the original source view. Both plain query timers call the inherited backend directly, with route-report construction outside the timer; there is no plain query-session reporting wrapper. No per-query SET, reconnect, policy collector or installation is added. Closed/replaced connections, binding mutation and execution errors poison the whole wrapped session; create a new session explicitly. No silent retry. A new session's full initialization is charged again.

## Operating scope and timing

The private restored database and snapshot are warm/shared. Each slot first runs exactly two native640 conditioning executions of that query on a separate reference reader; their outputs, wall boundaries and outer/SQL costs are recorded. Then a fresh measured session is constructed. Activation's primary endpoint is constructor + first full outer query time, including reader objects, **both** wrapped connections, security checks, settings/binding, envelope/query validation, predicate parsing, selection, SQL formatting/transport/decoding. Initialization is charged once, never amortized away. Reuse uses that same slot's readers after one discarded warmup, with three retained executions. Cleanup costs are recorded separately. Backend ordinary-native SQL latency is a secondary diagnostic only. No collector or P2 improvement is adopted.

Restore/import checks, shared snapshot load, references, qualification, conditioning and diagnostic post-slot settings audits are excluded from this explicitly restricted service endpoint, timed and recorded separately. They still consume the campaign budget. There is no cold-index/novel-query/production end-to-end claim. No GC/transport tuning, cache flushing, adaptive warmup, exclusion of slow rows or additional conditioning on failure.

The independent unit is the vector: cluster its filters, labels, rounds, repetitions and both blocks. Bootstrap10,000 resamples, seed20261019, sorted group order. Report pointwise95% intervals for mean outer gaps and mean log outer ratios; SQL diagnostics and block directions remain visible. Repeats are not extra independent samples.

## Six batches per reader

The persistent reader experiment groups the same 60 development batches into ten workloads of six batches, each spanning two intact vector blocks. Each workload runs under native, seed, and candidate, with two identical labels per family and three epochs. The six-label Williams order shifts by workload index plus twice the epoch index, using zero-based indices. The second epoch reverses workload order. Batch order rotates by 0, 2, and 4 positions across epochs, preserving order inside every batch. This balances each arm's slot and immediate predecessor across the experiment. Each arm opens one reader, creates one policy session if applicable, runs all six batches serially, and closes the reader. A policy installs on its first eligible request in batch 1 and stays installed for the remaining batches.

The primary endpoint is wall time per request across batches 2–6, including the transitions between batches. Record reader setup, the first batch with installation, and opening through closing separately. Every output and routing decision must match the sealed development evidence. Reuse the exact truth verified by the prior development run under the same input and native setting pins. Score the resulting 600 unique cases with the original recall gates and retain the original per-filter and overall bounds. Connection changes, extra installations, output mismatches, memory events, and deadline violations invalidate the run.

For steady-state timing, resample the ten workloads with all labels and epochs held together. Require every A/A interval to fit within ±0.10 ms per request and ±log(1.02). After those controls and recall pass, average each family’s two labels within workload and epoch. Require the upper 95% log-ratio limit below zero and mean savings in every epoch for the candidate against both native and seed. Preserve the full lifetime times as descriptive evidence.

The cap is 180 timed reader lifetimes, 10,800 search attempts, 120 policy installations, and one additional reader for the shared snapshot. The held guest keeps the original 32 GiB and four physical CPU guards. The preflight checks a two-hour wall limit. One future allocation requires a separate release with no retry.

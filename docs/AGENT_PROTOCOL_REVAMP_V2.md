# FANNAgent protocol revamp v2 — comprehensive execution plan

Date: November 13, 2026. Status: **proposed plan, not an activated protocol or authorization to spend**. This document follows the pre-revamp checkpoint commits `c3f7a48` and `6250bd4` on `feat/measured-policy-feedback`. It does not modify the sealed reader-attribution diagnostic, launch Torch, call a provider, generate replacement policies, or open validation/test.

The recommendation is to revamp the research procedure and its policy/runtime contract together, rather than simply ask the same model for more thresholds. First resolve the already-budgeted timing attribution question. Then qualify a cost-aware, unguarded action interface, rebuild development evidence for that interface, and run one prospectively bounded new episode. Negative and inconclusive outcomes are first-class results.

## 4. Redesign the executable policy interface

### 4.1 Derive observation plans from rules

Use a bounded causal DSL: published predicate identity; checkpoints16/32/64; qualifying count, tenth eligible distance, frontier gap and top-ten turnover; at most three ordered clauses per predicate and four comparisons per clause. Missing values make their comparisons false. No query IDs, fold IDs, exact labels, future traversal or predicted outcome values become runtime features.

The compiler derives a static predicate/checkpoint dependency mask. The agent does not emit an independent mask that can disagree with its rules. An empty branch means actual native continuation with no unnecessary observation pass for that branch. Skip complete feature passes only when their values and state are not needed later.

Turnover needs special care: turnover at32 depends on the declared preceding checkpoint16, and turnover at64 on32, not on whichever observation happened to be collected last. Compile those dependencies explicitly, including both full-top-ten availability flags. Gap and tenth distance can share one retained-heap collection. Do not claim independent per-feature cost if the implementation collects them together.

Every compiled artifact records canonical DSL/rule hash, observation/dependency mask, emitted-code hash, runtime profile and a human-readable explanation. For each case, masked and canonical unmasked observation must produce the same used feature values and first decision. Skipped or unreached checkpoints remain distinguishable.

### 4.2 Make partial stopping explicit

The unguarded objective accepts partial native answers, so the new interface should not automatically forbid every agent stop below ten candidates. Proposed v2 semantics permit a qualified causal stop returning the actual 0..10 eligible prefix; recall still charges every missing neighbor. Zero count is not automatically an exception, but a zero-answer policy must pass the same per-query preservation tests as every other program.

When fewer than ten candidates qualify, tenth distance and frontier-minus-tenth are unavailable; turnover is unavailable unless both relevant top tens exist. Count-only clauses can operate on the valid count. No fabricated distance, infinity sentinel or exact-label test may substitute for an unavailable feature. A decline continues the original search unchanged.

This requires a new, versioned runtime profile: remove the old unconditional count>=10 stop guard only for v2 programs. Legacy arms and the pending diagnostic remain byte-for-byte unchanged. Qualify each reachable forced checkpoint even when it has fewer than ten candidates, preserving traversal prefix and actual SQL output. Existing full-result proofs alone are insufficient. If partial-stop parity cannot be established within M1's fixed package, do not enable it or improvise labels; retain an explicitly scoped full-top-ten compatibility variant and report the limitation before generation.

### 4.3 Attribute engineering separately

Selective observation and partial-stop support are researcher-designed runtime capabilities. They are not LLM discoveries. Re-evaluate the three existing rules under compatible observation plans as an engineering/transfer ablation, preserving their original results. Do not rename those variants fresh agent outputs.

Give simple fixed-checkpoint and turnover comparators the same qualified capabilities. Native itself retains its actual ordinary path. No exact fallback is introduced to make a comparator pass.

First rescore all existing forced-stop outcomes against **raw** native640, not the guarded label. Recompute the safe-stop opportunity counts; the historical guarded total of1,930 is not automatically the ceiling for this problem. Obtain newly required partial-prefix outputs through M1 rather than inferring them from counts/distances.

The initial model context should be compact and filter-focused:

- Per-filter eligible fraction, raw baseline recall/returned-count distribution and query-group counts.
- Reached/available checkpoint counts; no-stop cases; forced-stop recall deltas and search-work reductions.
- Feature availability and dependency rules, measured observation/dispatch cost, continuation cost and uncertainty by condition.
- Fixed joint summaries or deterministic examples linking work saved to recall risk. Marginal safe/lossy bins alone are not separating-rule evidence.
- CPU/reader-qualified timing facts only. Label conditional estimates, extrapolations and cost surrogates explicitly. Do not present the current8.01%/6.54% gaps as proved benefits.

Version the guided primer/startup context too: remove guarded-completion assumptions, state raw/partial recall semantics, distinguish null feature availability from numeric values, and explain observation dependencies and measured cost categories. Provide semantic examples, not researcher-selected winning thresholds.

Do not pour all3,150 cases into the initial prompt. Keep full precision in the local evaluator and bounded counterexample retrieval. Examples use anonymous development ordinals only for explanation, never runtime matching. The five grouped folds are exposed-development diagnostics, not independent holdouts. None of the450 already-exposed groups may be relabeled as a pristine validation set.

Forced-stop opportunity is an oracle diagnostic upper bound: it does not establish separability by causal features, executable policy benefit or future-query safety.

## 6. Agent tools and research loop

Implement a versioned, transport-neutral campaign typed-action adapter that reuses existing budget, store and policy services. The present provider parser is Bash-only; native function-tool support needs implementation and testing. Preserve the general agent's existing Bash/backend API and calibration contracts. The model chooses hypotheses, features, predicates and thresholds. The controller validates structure, enforces scope/caps and records evidence; it does not fit thresholds behind the scenes.

| Proposed tool | Bounded response and authority |
| --- | --- |
| `inspect_workload` | Catalog/feature/dependency/cost summaries from the frozen development bundle; no arbitrary paths or query vectors in output. |
| `explain_cases` | At most12 anonymous cases per request, from an allowed development error/opportunity category. Never runtime oracle access. |
| `evaluate_candidates` | At most three DSL artifacts per invocation. Compile/validate, then replay every development case at full precision. Return per-filter/fold quality, stop counts, work, cost-surrogate breakdown and up to three counterexamples per failing condition. |
| `compare_candidates` | Compare already registered programs to native, simple rules and their matched observation/control paths. No new candidate generation or threshold search. |
| `submit_or_abstain` | Freeze eligible registered finalists or an explicit reasoned abstention; no validation/test execution. |

All evaluation feedback separates: (a) compiler/runtime validity, (b) observed recall preservation, (c) search work, (d) observation/decision/setup costs and (e) actual versus predicted full serving latency. A useful prediction is not an acceptance receipt. Exact labels may inform offline feedback but never compiled predicates.

Recommended loop: orient to scope/cost; state a testable hypothesis; submit a small batch; inspect exact recall counterexamples and where stop work repays observation; revise within the same ledger; conclude or abstain. Require concise evidence-linked explanations, not lengthy prose as a substitute for evaluation. Ask candidates to explain which filters continue and why. All six still count toward the objective.

No `find_best_threshold` endpoint, exhaustive hidden grid fitting, arbitrary shell/SQL/network execution, held-out tool, or unlimited adaptive data query is added. A host optimizer would be a separately named method and comparator, not invisible model assistance.

## 8. Candidate selection, controls and ablations

Keep all submissions and failed tests in a frozen registry. Among structurally valid candidates with zero development query losses, rank using the frozen full-serving-cost estimator, reporting uncertainty and all fold/filter behavior. Choose at most three live finalists: lowest predicted equal-filter mean; candidates within1% tie by fewer comparisons, fewer clauses, then canonical rule SHA256. Predictions determine only this development measurement shortlist, never final performance eligibility. Record every quality-eligible candidate not shortlisted and the stated rule. Freeze even an empty shortlist.

M5 measures each actual compiled finalist and its **matched continue-only control**: same inferred observation dependencies and decision code, with stop decisions forced to continue. Before a potential stop their state/feature work must match. Its extra later work is the intended counterfactual cost of continuing. It returns native output. This isolates learned stopping from its shared execution framework. Keep an old all-observe noop as a development engineering reference.

Required ablations and interpretations:

- Original three programs versus their compatible masked variants: runtime engineering/transfer, not new discovery.
- Native versus all-observe noop versus mask-matched continue-only: observation/path overhead or benefit.
- Each new policy versus its own continue-only control: incremental stopping effect.
- New policy versus simple fixed/count/turnover rules using the same capability and declared bounded tuning resources: model procedure versus simple policy search.
- Full versus partial fixed-checkpoint rules: value of accepting partial outputs under unchanged raw recall scoring.

Bound the simple-rule pool before evaluation: native five settings; fixed checkpoints16/32/64 in full-top-ten and qualified partial variants (six maximum); turnover32/64 with limits0/1/2 (six); two fixed historical comparators; at most three live new-agent finalists and three matched continue controls. Maximum25 selectable/control configurations; no opportunistic additions. Report all grid points. This is not a claim that an LLM must beat every simple rule to be useful automation, but any stronger claim requires that comparison.

## 9. Stable timing and evidence standards

Use M0 to choose and freeze the measurement contract before new model/live selection data. Counterbalance family assignments within backend processes and across physical CPUs where qualified. Record actual PID, affinity, order/predecessor and phase identity. Keep module/source/profile pins and before/after graph integrity. Do not subtract noop/A/B gaps, discard difficult filters or quietly choose a favorable reader.

Primary latency remains complete unguarded request time on an open reader, including collection, evaluation, search/continuation and decoding. Record map build, transaction/attach, warmup, close and lifecycle C/Q costs separately. Observation gating may change setup economics; do not hide those differences.

Work counters run in a separate stage/module. Report graph-score calls, queue/adjacency work and feature/member work with exact definitions, and demonstrate original/instrumented output/decision parity. Never blend counter-instrumented timings into the main endpoint.

Prefer the existing final five independent compatible allocations/four epochs, with every actual group/filter paired across families/labels. If M0 shows that this scheduling contract is inadequate, specify any replacement block/count/affinity design and its precision/resource consequences **before validation**, not after a failed final test. Do not claim repetitions or CPU slots are independent allocations.

Proposed confirmatory revamp adds the selected agent's matched continue-only control to the seven existing final families (eight families,16 labels). Three declared contrasts form one family: agent/native640, agent/matched-quality tuned native and agent/matched continue-only. Use one-sided upper98.333% ratio bounds (Bonferroni .05/3). The first two must be<=.95 for end-to-end practical success; the third must be<1 for incremental learned-stopping attribution. All relevant per-family/filter A/B90% hierarchical intervals must lie wholly within[.98,1.02]. If these fail, affected performance claims are inconclusive, not corrected by subtraction. This replaces the old two-contrast97.5% rule only if adopted in the new pre-holdout protocol.

Use20,000 paired hierarchical bootstrap draws, allocation then vector group, preserving every filter/family/label/epoch observation. Keep Holm across the twelve secondary agent/native scalar contrasts; per-filter matched-control contrasts remain descriptive unless a separate family is fixed prospectively. Report mean, median/p95, ratio, milliseconds, node effects and uncertainty limits. Planning order is M0 return -> M1–M3 implementation/qualification -> one M4 episode -> one M5 finalist cost package -> frozen M6 selection/test. The user approves a concrete prepared episode, not an unspecified research loop.

## 13. Replication and procedure-level robustness

A successful selected policy is not by itself evidence that the agent procedure is reliable. After the Small Reviews protocol is adopted, freeze the generation/tool/policy-selection method before applying it to additional sizes and the two additional datasets in the roadmap. Dataset-specific feature costs, schemas, splits and native settings may be qualified, but unsuccessful episodes must not trigger unreported prompt/action-space changes within that method version.

Initially budget one prospectively bounded episode per new workload and report every success, abstention, invalid candidate and performance-negative result. This supports scoped replication, not a strong estimate of model-run success probability. Any repeated-episode variability study needs its episode count, total candidate/charge budget and aggregation rule fixed before it begins. It cannot reuse validation feedback to choose a lucky episode; the entire applicable pool must be frozen before its one selection batch.

Keep transfer separate: an unchanged Small policy on another size/dataset tests policy transfer; regenerating a policy using the same procedure tests method replication. A query group exposed by Small test results is not a clean new held-out group merely because the corpus size changes. Audit aliases/overlap and preserve group roles/exposure records across sizes. Do not assume this proposal spends the project's broader budget or authorizes those future episodes.
